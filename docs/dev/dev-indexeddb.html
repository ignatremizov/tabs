IndexedDB Storage (Developer Notes)

Tree data is persisted in IndexedDB so it survives browser restarts. The background service worker owns all database access; UI views fetch tree data through emit('bkgd_getTree').

Database layout

Database name: TKTSTO. Object store:

  • Nodes — node records keyed by node ID.

Reconciliation

Browser events and view requests update the background tree directly, where NodeStore persists each actual change. Related node and parent records are committed in one IndexedDB transaction, and browser events are ordered with an in-memory mutex instead of a durable intent queue. A reconcile pass runs at startup and on the configurable periodicReconcile alarm to repair events lost while a Manifest V3 service worker was stopped.

Browser state is authoritative for currently loaded tabs and windows; the persisted tree remains authoritative for saved nodes. Browser-origin moves are not replayed from disk because their positional indexes become stale as soon as the live tab strip changes.

The former schema-2 Ops store has no compatibility migration. Moving from a build which used that schema requires exporting a backup, clearing extension data, and restoring the export.

See bkgd/reconcile.js for the repair pass which keeps tree state aligned with browser state.

How nodes are stored

Each node is serialized via Node.toDict() and stored by ID. The list of persisted fields is defined by Tree.dictable. Add new persistent fields by updating both Node defaults and Tree.dictable, and the field types in common/serialized-tree.js.

Key persisted fields

  • id, type, parent, nodes[]
  • label, note, title, url
  • windowId, tabId, loaded, wasLoaded
  • geometry, windowState, incognito
  • expanded, marked, checkbox
  • ctime, mtime, atime

Persistence flow

  1. Tree nodes live in memory in TreeStore (background).
  2. Mutations in the background use NodeStore, which calls db.writeNodes() after changes. Structural operations batch the changed node, old parent, new parent, and related pin/checkbox state atomically. Stale callbacks cannot save nodes already removed from the live tree.
  3. UI changes emit events to the background; background updates nodes and responds after the write transaction completes.
  4. On startup, TreeStore.loadTreeFromDB() loads nodes and rebuilds the tree from serialized data.

Backups vs IndexedDB

Backups are JSON exports generated from the in-memory tree (see Tree.downloadBackupNow()). These are separate from the IndexedDB storage and are meant for user-controlled archival or migration.

Where to look

  • bkgd/idb.js — database wrapper.
  • bkgd/treestore.js — loading/saving nodes.
  • bkgd/nodestore.js — write-through persistence on node edits.
  • common/tree.js — dictable field list.

Failed writes and durability

Successful mutation acknowledgements wait for the IndexedDB transaction to commit. A failed batch remains pending, including deletion tombstones, and can be retried with the sidebar's Retry saving button or by the next edit. Repeating an unchanged edit must not bypass a pending write. Generations queued during an earlier commit remain dirty until their own write succeeds.

The unsaved warning is separate from the transient status bar and is shown to newly opened sidebars too. Pending changes are held in memory: closing or crashing the browser before a retry succeeds can still lose those changes. Export a backup before closing when storage remains unavailable. Retry does not recreate browser tabs or replay already completed commands.

Import commit boundary

Imports are plain data, not Node properties to copy blindly. Validate known fields and their types, IDs, child arrays, and graph limits before constructing any nodes. The limits are 200,000 records, 400,000 edges, 512 levels including the destination root, 16 MiB per text field, and 128 MiB total text. The Options file picker also refuses files larger than 128 MiB before parsing.

Build the imported subtree detached from the live cache. Write its records and the new root child list in one IndexedDB transaction; publish the subtree only after commit. A failed import is not queued as an ordinary dirty edit. Concurrent edits retain their current in-memory root state and serialize their subsequent writes behind the import. Recoverable graph edges are skipped with visible warnings; disconnected records are retained beneath the imported root. Imported numeric browser bindings are discarded, but container scope and native group metadata remain available for safe later restoration.

Startup recovery

Startup reads all records before creating a fresh root. An empty database is a new installation; a missing root alongside other records is not. Cycles, unreachable or multiply owned records, mismatched keys, invalid field types, and excessive size/depth fail validation before the live model is replaced. Normal bounded trees are reconstructed iteratively. Recovery does not silently flatten or discard damaged data, and automatic cleanup runs only after a complete valid model exists.

Readiness promises reject on initialization failure so requests and sidebars do not wait indefinitely. The sidebar shows the underlying problem and an Export recovery data button when storage is available. The raw recovery format contains the original keyed IndexedDB values, including malformed JSON; it is a diagnostic file, not a normal session backup. Preserve it privately before any manual repair or reset. No reset or automatic repair is performed. Recovery export does not advance normal backup scheduling timestamps.
